## 一、架构总览

```
浏览器（React 19 SPA）
├─ main.jsx        登录闸 / 主题 / 语言 / 同步编排 / 计时器 / 全局动作
├─ store.js        localStorage 状态与账号归档
├─ photos.js       IndexedDB 位图
├─ remote.js    ── /api/state、/api/photo、/healthz（编译期摇树）
└─ views / chartview / drawer / components / chartkit（展示层）

Node http 服务（server/index.js）
├─ auth.js         会话解析（kimi Cookie / 反代头 / Bearer JWT）
├─ kimi.js         OAuth 授权码 + 本站 HS256 会话 + JWKS 验签
└─ db.js           mysql2 连接池 + family_state / family_photo

构建
├─ vite build      __SHARED_BACKEND__ / __DEFAULT_LANG__ 编译期常量 + DCE
├─ build-boot.mjs  服务端 → dist/server.bundled.js + dist/boot.js
└─ build-server.mjs 服务端 → dist-server/boot.js（1366KB 单文件）
```

**架构亮点（应保留）**

1. **双形态摇树真实有效**：对 `dist` 全量字节扫描（Node `Buffer.indexOf`）确认 0 处 `/api`、0 处 `/healthz`，说明静态形态确实没有把服务端代码带出去。
2. **单一派生入口**：`derive(records, photos)` 统一计算排序、分组、计数，视图只消费结果，避免多处口径漂移。
3. **乐观并发**：`family_state.revision` + `WHERE revision=?` + `affectedRows` 判定，是正确方向。
4. **安全底线扎实**：路径穿越归一化校验、照片 MIME 白名单、`nosniff`、无库 fail-closed、会话 HMAC `timingSafeEqual`。
5. **离线优先**：状态与位图本地留存，服务端不可用时界面不白屏（除登录闸，见 P0-01）。

**证据链**

1. [`src/auth.js:54-58`](../src/auth.js#L54-L58)：`__SHARED_BACKEND__` 为 false 时 `serverAvailable=false`、返回 null。

6. [`pages.yml:41`](../.github/workflows/pages.yml#L41) 用 `npm run build:static` 部署 Pages。

**实机验证**：本地以 `STATIC_DIR=dist` 启动服务端后访问 `/`，浏览器只显示「登录服务暂时不可用，请稍后刷新重试」与「重试」按钮，`#root` 仅 1 个子元素、1 个按钮，无底部导航栏，控制台无报错。

**建议（二选一，需产品决策）**

- 方案 B：Pages 部署改为注入式 auth（在 `index.html` 里加载 provider SDK），但这会引入外部依赖，且与「静态站零服务端」定位冲突。

**验收**：`npm run build:static` 产物在无任何后端环境打开，能看到完整应用主体并可新增一条记录、刷新后数据仍在。

## 三、P1 问题（本迭代内处理）

### P1-01 同步冲突整份覆盖，本地编辑静默丢失

**证据**：[`src/main.jsx:695-732`](../src/main.jsx#L695-L732)

```js
if (result.conflict && result.current) {
  revisionRef.current = result.current.revision || 0;
  skipPushRef.current = true;                       // 下一拍不回推
  setState((prev) => ({ ...prev, ...result.current.payload })); // 服务端整份覆盖
}
```

`payload` 包含 `records / photos / baby / metrics / faces / names / roleNotes / roles / extraMembers / typeOrder`，浅合并后本地新增记录直接消失；`skipPushRef` 又阻止把合并结果回推，等于本地改动永久丢弃。

**影响**：家庭多人同时记录（尤其两位家长同时段操作）必然出现「明明录了却没了」。

**建议**

- 冲突时先做**三方合并**：以 `baseRevision` 快照为基线，按 `record.id` 取并集、按 `updatedAt` 取较新版本；合并成功后再以新 revision 重推一次。
- 合并失败（同 id 内容冲突）时进入「冲突待处理」状态：保留本地副本到 `localStorage` 草稿区 + 顶部提示，而不是静默覆盖。
- 短期兜底：至少把冲突的本地 payload 写入 `baby-growth-log/conflict/<timestamp>`，提供恢复入口。

**验收**：两个浏览器上下文同时新增不同记录，冲突后双方最终各看到 2 条；无静默丢失。

### P1-02 登录闸 `redirecting` 死锁

**证据**：[`src/main.jsx:529-544`](../src/main.jsx#L529-L544) + [`src/auth.js:94-105`](../src/auth.js#L94-L105)

```js
if (__SHARED_BACKEND__ && serverAvailable && serverSignInUrl) {
  window.location.assign(serverSignInUrl);
}
return null;
```

当 `serverAvailable=true` 但 `serverSignInUrl=null`（服务端配了 auth 但没配 `AUTH_SIGNIN_URL`，`authInfo().signInUrl` 为 null，见 [`server/auth.js:38-41`](../server/auth.js#L38-L41)），函数既不跳转也不抛错；`main.jsx` 的 `if (user)` 分支不成立，`gate` 永久停留 `redirecting`，GateScreen 此时没有重试按钮。

**建议**：`startSignIn()` 返回值语义化（`{ navigated, user, reason }`），`redirectToSignIn` 对 `navigated=false && !user` 落回 `unavailable` 并提示「登录入口未配置」；GateScreen 在 `redirecting` 超过 8 秒后提供「返回/重试」。

**验收**：构造 `AUTH_JWKS_URL` 已配、`AUTH_SIGNIN_URL` 缺失的环境，页面 10 秒内给出可操作提示而非无限转圈。

### P1-04 OAuth `state` 未绑定浏览器会话（登录 CSRF / 账号混淆）

**证据**：[`server/kimi.js:55-75`](../server/kimi.js#L55-L75) 的 state 为 `base64url(redirect_uri) + HMAC`，不含随机 nonce，也未与浏览器已有的临时 Cookie 绑定；回调只校验 HMAC 与过期。

**影响**：攻击者可诱导受害者用攻击者发起的 `code` 完成回调，使受害者浏览器被种上攻击者账号会话（login CSRF）；受害者的家庭数据会写入攻击者账号。

**建议**：发起登录时生成 32 字节随机 `nonce`，写入 `HttpOnly` 短期 Cookie（`bgl_oauth`，10 分钟），state 携带 nonce 的 HMAC；回调同时校验 Cookie 与 state 的 nonce 一致，用后即焚。

**验收**：缺失/不匹配 nonce 的回调返回 400，且不种会话 Cookie。

### P1-05 纯 HTTP 部署下会话 Cookie 失效

**证据**：[`server/kimi.js:92-105`](../server/kimi.js#L92-L105)

```js
localhost ? "SameSite=Lax" : "SameSite=None; Secure"
```

非 localhost 且站点为 `http://`（NAS 内网、IP 直连、未配 TLS 的临时环境）时，浏览器会拒绝 `Secure` Cookie，登录后立即丢失会话，表现为「登录成功又回到未登录」。

**建议**：根据 `X-Forwarded-Proto`/`req.socket.encrypted` 判断协议；HTTPS 用 `None; Secure`，HTTP 用 `Lax`（并明确告警）。更彻底的做法是强制 HTTPS 部署（Caddy 已具备）。

**验收**：`http://192.168.x.x:3000` 下登录态可保持；HTTPS 下跨站回跳正常。

### P1-07 私有家庭照片被标记为公共可缓存

**证据**：[`server/index.js:230-233`](../server/index.js#L230-L233)

```js
return send(res, 200, row.bytes, {
  "content-type": mime,
  "cache-control": "public, max-age=31536000, immutable",
});
```

`send()` 默认 `no-store`，此处被覆盖为 `public`。经过 CDN/企业代理时，家庭照片可能被缓存并被其他请求命中。

**建议**：改为 `private, max-age=31536000, immutable`；若走 Caddy/CDN，增加 `Cache-Control: private` 与 `Vary: Cookie`。同时确认 `?family=` 不参与缓存键。

**验收**：响应头为 `private`；不同 `family` 参数不会互相命中缓存。

## 七、结论

- **架构方向正确**：双形态摇树、单一派生、乐观并发、安全底线都属于「可长期演进」的设计，不需要推倒重来。
- **问题集中在「最后一公里」**：静态形态的门控策略、冲突合并策略、发布物清洁度、跨平台构建、自动化门禁。
- **风险排序建议**：先修 P0-02（隐私，不可逆）→ P0-01（可用性）→ P0-03（可回滚基线）→ P1-01/02（数据与登录）→ 其余按路线图推进。
