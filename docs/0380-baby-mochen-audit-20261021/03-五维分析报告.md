## 一、时间维度（Time）

### 1.1 现状测量

| 指标 | 实测/推算 | 评价 |
| --- | --- | --- |
| 静态构建耗时 | 1.18s（Vite 6） | 优秀 |
| 服务端打包 | esbuild 单文件 1366KB | 可接受 |
| 首屏 JS | 339.17KB / gzip 105.85KB | 可接受（未做路由级拆分，但单页无路由） |
| 首屏 CSS | 63.34KB / gzip 12.81KB | 良好 |
| 首屏字体 | **7.42MB 单文件** | **主要瓶颈** |
| 私人照片随包 | 10.57MB | 与用户首屏无关，但拖慢部署与 Pages 发布 |
| 同步延迟 | 600ms debounce 后推送 | 合理（牺牲实时性换请求量） |
| 会话 TTL | 30 天 | 合理；缺少刷新/滑动续期 |
| JWKS 缓存 | 10 分钟 | 合理；缺少 `kid` 未命中即时刷新 |
| 测试反馈环 | 无自动化测试 | **最长反馈环：靠人工** |

### 1.2 关键判断

- **时间成本不在构建，而在「字体下载」与「人工验证」**。字体单文件会显著推迟中文首屏可读时间（4G 网络下 7.42MB 约数秒到十几秒，取决于带宽），且 `font-display: swap` 会造成明显字形跳变。
- 没有测试意味着每次改动的验证时间不可压缩，也无法在 CI 中提前发现回归。

### 1.3 改进建议（按收益排序）

1. 字体分片：按 `unicode-range` 拆为 3–6 个子集（常用 3500 字 / 扩展 / 拉丁），首屏只拉常用子集；或直接使用系统字体栈（`-apple-system, "PingFang SC", "Microsoft YaHei"`），把 7.42MB 降为 0。
2. CI 增加 `npm ci` 缓存与构建产物缓存（当前已有 `cache: npm`，可再加 Vite 依赖预构建缓存）。
3. 建立「提交前 30 秒自检」：`lint + unit` 本地钩子，把反馈环从「人工 10 分钟」降到「30 秒」。
4. 同步 debounce 保持 600ms，但冲突重推增加指数退避，避免弱网下高频重试。

## 二、空间维度（Space）

### 2.1 代码空间

| 模块 | 行数量级 | 组织评价 |
| --- | --- | --- |
| `main.jsx` | 1487 行 | **过大**：登录、同步、计时器、动作、渲染编排混在一处，建议按 `useAuthGate`、`useSync`、`useTimer` 拆 hooks |
| `views.jsx` | 1024 行 | 偏大，但按视图分区清晰，可接受 |
| `drawer.jsx` | 714 行 | 偏大，表单/详情/灯箱可拆文件 |
| `styles.css` | 2412 行 | 偏大，建议按 `base/layout/views/components` 拆分并纳入构建 |
| `server/index.js` | 330 行 | 合理 |
| `server/auth.js` / `kimi.js` / `db.js` | 138 / 250 / 124 行 | 合理 |

**空间问题**：

- 根目录 `assets/`（13.84MB）与 `public/assets/` 重复，属于历史构建副本，是典型的「空间债」。
- `dist` 25.16MB 中，真正运行必需的 JS/CSS 仅约 0.4MB，**98.4% 是字体与私人照片**。
- `public/` 24.77MB 里，产品素材与私人照片混放，缺少目录职责边界。

### 2.2 数据空间

- `family_state.payload` 为整份 JSON `LONGTEXT`：单家庭写入随记录增长而线性膨胀，每次同步都全量传输。记录上百条后，单次 PUT 可能达到数百 KB 到数 MB。
- `family_photo.bytes` 为 `LONGBLOB`，单图上限 12MB，MySQL `max-allowed-packet=64M` 已预留；但**无孤儿回收**，删除记录不删照片会持续占用空间。
- 照片 GET 被标记 `public` 缓存（P1-07），在 CDN 场景会额外放大「可被复制」的空间暴露面。

### 2.3 改进建议

1. 删除根 `assets/`，统一以 `public/assets` 为唯一素材源；`.gitignore` 兜底。
2. 私人照片移出仓库；`public/` 只保留 ≤ 2MB 的演示素材。
3. `family_state` 拆分：`family_record` 行级存储 + `revision` 表，把「全量覆盖」改为「增量变更」，同时天然支持冲突合并（按 `record.id`）。
4. 增加照片引用计数或定期 GC（`NOT EXISTS` 于 payload 中的 `blobId`）。

## 三、属性维度（Attribute）

| 质量属性 | 评分 | 证据 | 缺口 |
| --- | --- | --- | --- |
| 功能正确性 | 60 | 静态站不可用、冲突丢数据 | 门控策略、合并策略 |
| 性能 | 72 | JS gzip 105.85KB；字体 7.42MB | 字体分片、状态全量同步 |
| 安全 | 68 | 穿越防护、MIME 白名单、nosniff、fail-closed | OAuth state、Cookie 策略、照片 public 缓存、静态头缺失 |
| 可靠性 | 65 | 无库降级正确、推失败不白屏 | 无请求超时、无优雅退出、照片上传失败静默 |
| 可维护性 | 58 | 注释质量高、命名清晰 | 缺 lint/测试；`main.jsx` 过大；指标 ID 有西里尔字母 |
| 可移植性 | 55 | 双形态设计优秀；Docker/systemd/Pages 三套部署 | Windows 构建失败；部署链路未验证；`.env` 引号问题 |
| 可访问性 | 52 | `aria-live` 通知、部分 Esc 处理、`aria-label` 较全 | 抽屉无焦点陷阱/`aria-modal`；对比度未测；键盘全流程未测 |
| 可观测性 | 35 | 有 `console.error` 分类（oauth 失败原因） | 无结构化日志、无请求 ID、无指标、无健康度细分 |

**属性结论**：安全底层实现质量高于同类个人项目，但「策略层」有明显漏洞；可观测性是最大短板——线上出问题时只能靠用户描述。

**建议**

1. 引入 `pino`（或轻量 JSON logger），记录 `requestId / userId / family / route / status / duration`；错误按 `why` 分类已有基础。
2. `/healthz` 拆分 `liveness` 与 `readiness`（后者探测 DB）。
3. 补一条 a11y 检查（`axe-core` 集成到 Playwright 冒烟）。

## 四、事件维度（Event）

### 4.1 事件流梳理

| 事件 | 处理方式 | 风险 |
| --- | --- | --- |
| 应用启动 | 读会话 → 判 `gate` | 静态形态必进 `unavailable`（P0-01）；`signInUrl` 缺失会卡 `redirecting`（P1-02） |
| 状态变更 | 600ms debounce → PUT → revision 更新 | 冲突整份覆盖，本地丢失（P1-01） |
| 会话变化 | `subscribeSession`（仅注入式支持） | 服务端 Cookie 过期无主动探测，需刷新页面才感知 |
| 照片录入 | EXIF → IDB → 可选远端 PUT | `putPhotoBlob` 返回值被忽略；上传与状态写入无一致性（P2-06） |
| 计时器 | 组件内存态 | 登录/退出 `closeAllSheets()` 会清空；刷新丢失（设计如此，但无提示） |
| 删除记录 | 确认弹窗 → 删状态 + 可选删照片 | 远端照片删除失败被吞（`dropPhotoBlob` catch） |
| 退出登录 | 归档 → 重置 → 跳授权 | 归档依赖 `localStorage`，容量满时可能抛错且无提示 |
| OAuth 回调 | state 验签 → 换 token → 种 Cookie | state 无 nonce 绑定（P1-04） |

### 4.2 事件设计评价

- **好的部分**：`skipPushRef` 防止「拉下来又推回去」的自激循环；`writeDenied` 防止未登录反复 401；`alive` 标志防止卸载后 `setState`。
- **坏的部分**：冲突事件被当作「覆盖」而不是「协商」；上传失败事件被当作「成功」；登录失败事件在 `redirecting` 分支没有出口。

### 4.3 改进建议

1. 冲突事件模型化：`ConflictState = { local, remote, base }`，UI 顶部出现「有更新冲突，查看并合并」。
2. 上传事件状态机：`pending → uploaded → failed`，失败的 blob 进入重试队列（页面可见角标）。
3. 会话过期事件：所有 `fetch` 拦截 401 → 主动 `readSession()` → 必要时跳登录，而不是静默降级为 `writeDenied`。

## 五、关联维度（Association）

### 5.1 组件与模块依赖

| 关联 | 评价 |
| --- | --- |
| 前端 ↔ 服务端契约 | 仅靠手写 `fetch` + 注释，无 OpenAPI/JSON Schema，字段漂移不可检测 |
| 前端 ↔ 数据库 | 无直接关联，符合分层 |
| 编译期常量 ↔ 构建脚本 | `__SHARED_BACKEND__` 与 `BUILD_TARGET` 强耦合，跨平台脚本破坏该关联（P1-03） |
| CI ↔ Pages | 两套 workflow 重复断言，规则不一致风险（如 `grep` 用法） |
| 部署 ↔ 运行 | `deploy/.env.example` 的引号与 `boot.js` 解析器不匹配（P2-09） |
| 图片素材 ↔ 代码 | `glyphArt`/`sceneArt` 为硬编码路径，缺失时回落图标（设计良好） |
| 文档 ↔ 代码 | README 的公网演示、登录降级描述与实际不符；旧审核文档与 git 状态不符 |

### 5.2 生态位判断

- 作为「家庭内部工具」，本项目的外部依赖极少（React + mysql2），供应链风险低，可长期维护。
- 作为「可复制模板」，缺少配置化与测试，复制成本主要在「理解 `main.jsx`」与「重跑部署」。

### 5.3 改进建议

1. 用 JSDoc + `zod`（或手写 schema）定义 `payload` 契约，前后端共用一份校验，CI 做往返测试。
2. 统一 CI/Pages 的断言脚本到 `scripts/assert-dist.mjs`，避免两处维护。
3. README 增加「能力矩阵」：每个部署形态哪些功能可用、哪些不可用，并与 E2E 断言绑定。
4. 旧文档归档到 `docs/archive/`，在当前索引中标注有效版本。
